# IPC 契约的成熟度评估

> **这份文档回答什么问题**：`DougongDesktop.Ipc` 的协议设计，能不能支撑
> 将来的第二个客户端（web / 远程）？如果不能，缺什么？
>
> 结论先说：**设计思路够格，完成度不够**。单人单连接下不缺任何东西；
> 一旦出现第二个客户端，有三处必须先补。

评估时间：2026-10-30。评估对象：`src/DougongDesktop.Ipc/`
（`Protocol.cs` 303 行、`IpcConnection.cs` 170 行）。

---

## 一、做对的部分

这些是**实测过的**，不是设计意愿：

| 项 | 现状 | 依据 |
|---|---|---|
| 双向契约完整 | 8 个 `ClientCommand` + 8 个 `ServerEvent`，`method` 做多态判别 | `Protocol.cs` |
| 序号单一来源 | 会话事件与引擎状态事件共用 `IpcServer.NextStatusSequence` | 核实过：`SessionRuntime` 的 `nextSequence` 参数就是它 |
| 传输选型清醒 | NDJSON over TCP 而非命名管道 | 注释写明理由：跨平台一套代码，且能 `nc` 上去手调 |
| 整条发送而非 delta | `ItemAddedEvent` 整条发，客户端不做增量合并 | 注释：避免客户端合并状态出错 |
| 一个踩过的坑已记录 | `SendAsync` 必须按基类类型序列化，否则判别字段丢失 | 实测到的现象是 "Read unrecognized type discriminator" |

**这些决定了它值得保留。** 将来抽包不是重写，是补齐。

## 二、三处撑不住第二个客户端

### 2.1 没有版本协商

`SessionOpenedEvent` 加字段、`ToolCallItem` 改语义——**老客户端会静默错**。

桌面端是同版本发布，所以现在没事。但 web 客户端版本一定滞后（浏览器缓存、
用户不刷新），远程客户端更是无法要求同步升级。

**代价**：协议一旦发出去就不能安全地演进。加字段看起来安全，但"客户端不认这个
字段"和"这个字段确实为空"在 JSON 里长得一样。

### 2.2 没有鉴权

`IpcConnection.ConnectAsync(endpoint)` 直接连，端点文件就是全部凭证。

`IpcConnection` 的注释里写得很清楚：

> 安全边界是"仅回环 + 端点文件仅当前用户可读"，这不是对同用户恶意进程的沙箱

**这对本地 IPC 是正确判断**。但任何非回环的监听（web 必然如此）都需要真正的
鉴权——token、会话 cookie、或者别的。这一条工程量最大，因为要连带决定
"谁能看哪些会话"。

### 2.3 序号不能支撑长连接恢复

序号本身是对的（单一计数器、严格单调）。缺的是**恢复语义**：

- 断线期间**没有事件**时：重连后第一帧的序号远大于本地记录，
  看起来像漏了几千条，实际只是间隔期没有事件。
- 断线期间**真跑了事件**时：需要判断"快照之后哪些帧是新增的"。

两者都要求服务端提供「从某个序号开始回放」的能力。**现在没有。**

> **顺带修了一处**：`ServerEvent` 的注释原先写着"序号不连续时必须请求重新同步"，
> 但**没有任何代码实现**这件事。已改成三档如实说明（怎么分配 / 现在没人在检测 /
> 将来要补什么）。契约里没实现的条款比没有条款更危险——有人会按它去写增量同步，
> 然后踩到"看起来能用、断线后才错"的坑。

## 三、别的项目怎么做的（源码对照）

| 项目 | 做法 | 规模 |
|---|---|---|
| dsh (`packages/api/gateway`) | 双向 Typert RPC，Host/Client 各一个 Cordis 环境，方法级权限策略 | 3044 行 gateway + 独立 `remote-access` 包 |
| pi.net (`Pi.Protocol`) | 4 字节大端长度前缀 + CBOR 分帧 | 532 行，只做分帧不碰业务 |

**dsh 那套是为多租户准备的**：`account-controller`（多用户）、
`remote-access`（角色/资源级策略）、`job-controller`（作业调度）。
我们要做的不是那个——**单人 agent 不需要多租户模型**。

pi.net 的 `Pi.Protocol` 更简单，但它服务的是「远端执行环境」（`Pi.Env`，
3000+ 行含 SSH），我们不做那个场景。

**结论：两家的做法都不用照搬。** 我们的契约比 pi.net 更贴业务（有会话、条目、
审批），比 dsh 简单得多（无多租户）。这个位置是对的。

## 四、什么时候该抽 `Dougong.Protocol` 包

**抽包的门槛不是"协议写好了"，是"有第二个消费者要复用它"。**

### 抽的触发条件（满足任一）

1. **出现第二个非终端 UI 客户端** —— 比如 web、远程客户端、或者移动端。
   这时的关键判断：新客户端**能不能不改协议形状就用上**。
   能，就抽包；不能，先改协议，别急着抽。

2. **Desktop 需要与 AgentHost 分仓发布** —— 两个仓库要各自引用同一份契约。

3. **第三方要写自己的宿主** —— 有人想用 Dougong SDK 做自己的 UI，
   而我们的 IPC 契约正好是他们要的东西。

### 不抽的理由（现在的情况）

- **只有一个消费者**（Desktop 的 AgentHost + UI，同仓库同版本）
- 抽出去之后接口会按"Desktop 怎么用"来设计，等真有第二个宿主时又得改
- 这与 TUI 那件事是同一个判断（SDK 侧 `architecture.md` §2.2 有同样记录）

### 抽之前必须先补的三件事

**顺序不能颠倒**——先补能力，再抽包：

| 顺序 | 补什么 | 为什么必须在抽包之前 |
|---|---|---|
| 1 | **版本协商** | 抽成包就意味着有对外版本承诺，没有协商能力的协议不能对外 |
| 2 | **序号回放**（按序号从某点重发） | 长连接恢复的前提；没有它，第二个客户端一断线就要全量重拉 |
| 3 | **鉴权** | 只有在真做非回环客户端时才需要；本地 IPC 不需要 |

前两件在**只有桌面端时也能做**，而且成本不高（加字段 + 加一个回放接口）。
**第三件只在真要做远程/web 时才有意义**，不要为它提前设计。

### 抽包后不应该包含的东西

- **不包含多租户/账户模型**：那是 dsh 的需求（它是完整产品），不是 SDK 的
- **不包含 UI 相关的投影决策**：比如"条目怎么分组显示"属于宿主
- **不包含传输实现绑定**：契约只定义消息形状，TCP/管道/WebSocket 由宿主选

## 五、一句话结论

**赌得起的是设计思路，不是完成度。**

现在的协议形状（`method` 判别 + `Sequence` + `Snapshot`）已经给版本协商和回放
留了位置——补的是字段与语义，不是重设计。这决定了将来抽包是**增量**而不是重写。

但**不要因为"将来可能会抽"就去补现在不需要的东西**。
单人单连接下，这三处缺口一个都不会暴露。提前补齐等于为想象中的需求付维护成本。
